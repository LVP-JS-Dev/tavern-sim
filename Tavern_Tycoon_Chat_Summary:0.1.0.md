## 6) Core: декомпозиция на независимые части и контракты

Пользователь: «Цель получить максимально независимые части и фиксация контрактов между нами. Из чего состоит core?»

Мы разложили core на модули (и уточнили что адаптеры отдельно):

### 6.1 Core-модули (рекомендованный состав)
1) **Shared Contracts**
- Типы: `GameState`, `Action`, `DomainEvent`, `DomainError`
- `Clock`/время для детерминизма (или передача `now` в action)

2) **State Model**
- Весь state сериализуем в JSON
- Версионирование и миграции

3) **Economy Engine**
- Доход, стоимость апгрейдов, мультипликаторы

4) **Progression & Rules**
- Правила апгрейдов (can/cannot + причины)

5) **Time & Offline Simulation**
- Пересчёт времени, оффлайн симуляция

6) **Content / Data**
- Конфиги (герои, баланс, коэффициенты)

7) **Actions API / Use-cases**
- Единая точка входа для UI: `dispatch/reduce`

### 6.2 Не-core (адаптеры)
- UI (CLI/React-текст)
- Persistence (LocalStorage/файл)
- Платформенные интеграции
- Аналитика

### 6.3 Контракты “между нами” (что фиксируем жёстко)
- Contract GameState (типы + инварианты)
- Contract Action (перечень действий + payload + ошибки)
- Contract Economy (формулы, округление, капы)
- Contract Offline (дельта, cap, summary)
- Contract Config (схемы валидации)

## 7) Глубже про GameState: декомпозиция на под-состояния

Пользователь: «Можем ли мы еще глубже декомпозировать gamestate?»

Мы предложили разбиение `GameState` на независимые slices:

- `meta` (version, createdAtMs, lastSeenAtMs, rng)
- `wallet` (gold, lifetimeEarnedGold, валюты)
- `tavern` (level, upgrades)
- `heroes` (roster, order, unlocks)
- `time` (lastTickAtMs)
- optional:
  - `daily`
  - `unlocks`
  - `journal` (domain events log)
  - `cache` (income cached)

Инварианты:
- сериализуемость
- согласованность ссылок (order ⟂ roster)
- не хранить вычислимое как истину (кэш необязателен)

## 8) Actions и Flux-подобная архитектура

Пользователь: «Actions? То есть у нас будет flux подобная архитектура?»

Мы зафиксировали позицию:
- Да, **по форме** похоже на Flux/Redux, но это не про UI.
- Это про **контракт переходов состояния** (domain-first).

Рекомендованный контракт:
- `reduce(state, action) -> { state, events, error? }`
- UI/CLI становится “тонким”: отправляет actions, читает state, реагирует на events.

Также перечислили альтернативные стили архитектуры (см. ниже).

## 9) Альтернативные варианты архитектуры (обзор)

Пользователь: «Какие еще могут быть варианты архитектуры?»

Мы перечислили основные альтернативы:
1) Reducer + Actions (Flux-like)
2) Use-case API (команды как функции)
3) FSM для flow-состояний
4) CQRS-lite (разделение read/write моделей)
5) Event Sourcing (события как истина, чаще overkill на alpha)
6) ECS-подобная модель (для множества сущностей и систем)
7) Data-driven rule engine (баланс в конфиге)

Рекомендация для нас на Alpha:
- Reducer/Actions + slice-модули + (опционально) CQRS-lite через selectors/read-model.

## 10) Events в Action-подходе: зачем они

Пользователь: «Зачем events? Разве не достаточно вернуть новый стейт?»

Мы пояснили:
- Вернуть только state можно, но тогда UI вынужден делать diff и “догадываться”, что произошло.
- `Action` = намерение, `Event` = факт/результат.
- Events нужны для:
  - UI реакций (toast, сообщения, “level up”)
  - логирования/аналитики
  - достижений/триггеров без расползания логики в UI
  - объяснимости (“что случилось при действии”)

Важно: это не event sourcing, а “список фактов” по итогу одного действия.
